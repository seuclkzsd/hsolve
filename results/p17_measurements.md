# P17：AVX-512 打包、DGEMM 线程划分与 BLR 实验

2026-10-16，gpu02，双路 Xeon Silver 4314。**本轮没有采用新的求解器优化：打包改写在同库开关对照中基本持平，线程划分和默认 BLR 配置更慢。112/112 次完整求解通过独立验收。** 保留实验原型及正、负结果。求解器仍使用 P15 的二进制；工作区保留的工具改动是修正分解筛查的候选执行顺序。

逐次数据与日志见 [p17_measurements.json](p17_measurements.json)，工具改动见 [p17_candidate.patch](p17_candidate.patch)。原始记录、探针、实验源码、基线和候选二进制归档于 `/tmp/os2026-p17-results.tar`；本机与 gpu02 各一份。依赖的 MUMPS 和 OpenBLAS 库仍位于集群环境，路径及哈希在 JSON 中。大矩阵输入和完整求解的特征向量不收入归档。

## 条件与有效性

- 所有编译、探针、计时与独立验收在 gpu02 执行。完整小例计时使用 `16-31`、16 个物理核、32 GiB；固定排序的分解筛查使用 `16-23`、8 核，模拟一个证书辅助进程；均用 `guard.py --exclusive`。
- 百万阶完整求解使用 `8-15,16-23`，双插槽各 8 核，总计 16 核、32 GiB，三个 MPI 进程（主进程加两个证书辅助进程）。此时停止同核范围的构建和独立验收任务。
- 构建、探针及单独验收使用 `8-15`、12 GiB。每次完整求解保持原始目标和容差，适用的默认 exact 证书保持开启。
- 完整求解时间为报告的 `time_total_s`，排除程序启动、读入和写出。单次分解筛查只测固定排序后的数值分解，不能代替完整求解。

本轮没有重测 SLEPc。最近的直接对照仍为 [P15](p15_measurements.md)：腔体 hsolve 0.224234 s / SLEPc 0.214029 s；百万阶 Yee hsolve MPI 53.060056 s / SLEPc 50.976600 s，分别慢 4.77% 和 4.09%。跨批次数据不拼接成新的加速比，仓库调优的 SLEPc 对照也不等于覆盖所有开源实现。**尚未证明所有算例不慢于开源方案。**

## 百万阶精确计数的热点

固定百万阶 Yee 排序，在下端点做一次 8 线程精确计数。主线程每 500 微秒采样一次，共 43,548 个样本；数值分解约 21.87 s，负惯性 337610、零主元为 0。采样与内存拦截仅用于诊断，不用其时间计算加速比。

| 分类 | 主线程墙钟样本占比 |
|---|---:|
| BLAS 计算核 | 56.95% |
| BLAS 数据打包 | 13.43% |
| MUMPS 面板 | 9.02% |
| 自旋等待 | 6.06% |
| 内存清零 | 4.57% |
| MUMPS 装配 | 4.04% |
| 其他复制 | 3.80% |

其中 `dgemm_oncopy_SKYLAKEX` 占 9.93%，`dgemm_itcopy_SKYLAKEX` 占 3.30%。这是主线程墙钟分布，不是所有线程的 CPU 时间分布。

## AVX-512 两列打包原型

安装的 OpenBLAS 0.3.34 SkylakeX 构建使用 `dgemm_kernel_16x2_skylakex.c`，外部输入打包布局来自 `gemm_ncopy_2.c`。实验库替换其内部 `dgemm_oncopy_SKYLAKEX` 符号：每次读两组 8 个 double，通过两次 AVX-512 双源排列交错存储；尾部使用掩码，奇数列直接复制。没有浮点算术，目标是保持所有输入位模式。

基础版 37,500 组检查、多列组版四种设置各 37,500 组、预取版三种设置各 37,500 组，总计 **300,000 次逐位检查全部通过**。探针同时对照安装的 OpenBLAS 和独立布局模型，覆盖零尺寸、奇数列、不同步长和偏移、向量边界、保护页，以及 signed zero、非规格化数、无穷和 NaN 的位模式；检查输入未被改写和输出填充区未被破坏。不同设置复用了同组输入，不能将总数解释为 300,000 种独立形状。

原型保留 `gemm_ncopy_2.c` 的 UT Austin 版权与 BSD 许可。它针对该安装库的内部 ABI，不能直接当作通用 BLAS 实现发布。

|---|---:|---:|---|
| 两列 AVX-512 | 3 | 21.8061 | 21.6547 |

基础版约低 0.69%；多列组和预取没有增加清晰收益。基础版 L0 下时间从 10.3219 s 降至 10.2026 s，节省主要发生在 L0 子树内。

## 独立划分大 DGEMM 线程：不采用

实验拦截器只对较大的 NN DGEMM 划分互不重叠的 C 块，由外层 OpenMP 调度，每块调用现有单线程 BLAS。8 线程下分别尝试 1、2、4 个行分块，其余线程沿列分块。三个设置各 216 次与原 BLAS 的数值对照全部通过，最大缩放差为 5.75571e-17；这不是逐位一致的结果。

每配置一次的百万阶分解：基线 21.7919 s，三个候选分别为 21.9307 / 23.0147 / 24.0268 s，均未改善。syn-mem27-46 同样变慢。L0 下时间约 10.32 s 不变，退化发生在 L0 以上的线程化调用。因此不进入求解器，也不继续完整求解测试。

四组固定排序筛查共 **70 次计数**，全部正常完成、惯性有效且与各批基线相同。另有一次绑定诊断和一次采样诊断，不计入 70 次筛查或完整求解验收数。


## 百万阶完整求解：初步收益未在确认对照中稳定复现

先以无预加载的基线与两列打包候选交替运行各三次，再增加一组同库开关对照：两边都加载相同 `pack.so`，关闭方只将调用转发给原 OpenBLAS，以减少预加载和内存布局差异的干扰。两组均使用同一个 P15 MPI 可执行文件、相同配置和核心布局，适用的 exact 证书开启。

| 批次 / 配置 | 中位数 s | 范围 s | 候选 / 基线 | 独立验收 |
|---|---:|---:|---:|---:|
| 初测 / 无预加载基线 | 53.643230 | 53.130252–53.877684 | — | 3/3 |
| 初测 / 打包候选 | 52.773378 | 52.577411–53.062080 | 0.9838 | 3/3 |
| 确认 / 同库关闭打包 | 53.373111 | 52.975360–53.621936 | — | 3/3 |
| 确认 / 同库启用打包 | 53.360190 | 52.842638–53.723805 | 0.9998 | 3/3 |

首批中位数降低 1.62%，其中迭代阶段中位数从 11.5296 s 降至 11.0115 s，回代量均为 120。确认批次的迭代阶段反而从 11.3566 s 增至 11.4609 s；三个配对中有两个启用版更慢。确认批次完整中位数只低 **0.024%**，范围重叠，不能支持稳定的完整求解加速。

确认批次的数值分解中位数为 15.1681 / 15.0039 s，证书阶段为 23.0085 / 22.9154 s，仍提示局部打包成本略降；但最终采用依据是完整求解，不能只选局部节省或第一批最快结果。本轮保留原型，不加入默认依赖或内部符号拦截。

七个小例 98 次、百万阶打包两批 12 次、BLR 对照 2 次，共 **112/112 次完整求解通过独立验收**。百万阶均与完整参考集一致，原始 1e-10 容差及精确证书保持不变。

## BLR 主分解：当前配置不采用

百万阶 Yee 单次完整求解对照，双插槽 16 核、三个进程。唯一配置差异是 `blr=on`；采用现有默认压缩阈值 `blr_tol=1e-10`，双精度迭代修正、修正失败回退及 exact 证书均保留。两次都通过独立完整验收，BLR 实际生效，没有触发全秩回退。

| 项目 | 全秩基线 | BLR |
|---|---:|---:|
| 完整求解 s | 53.2634 | 59.3168 |
| 数值分解 s | 14.78 | 14.17 |
| 分解阶段（含分析等）s | 18.4382 | 18.6524 |
| 迭代 s | 11.2527 | 16.7990 |
| 回代右端向量数 | 120 | 275 |
| 验证 s | 0.1298 | 0.4495 |
| 精确证书 s | 23.1410 | 23.1093 |
| 进程树峰值 GiB | 24.679 | 22.860 |

压缩减少了内存和部分数值分解成本，但分析、修正及更多迭代抵消收益，完整时间增加约 11.4%。这只是当前排序和默认 BLR 阈值的一次筛查，不代表所有 BLR 配置都无效；足以排除直接把现有 BLR 默认打开作为本例的性能优化。

## 保留的工具修正与交付检查

`tools/bench/factspeed_screen.py` 旧逻辑先循环移位，再在奇数轮反转。两候选时得到 AB / AB；四候选前两轮为 ABCD / ADCB，基线都在第一位。现移除奇数轮反转，只循环移位：两候选为 AB / BA，四候选在四轮内各占每个位置一次。重复数不足候选数时仍不能称为完全平衡的顺序。

该修正不改变数值求解器。完整求解的 `ab_cases.py` 和 `compare.py` 原本就正确交替 / 轮转，不受该问题影响。此前分解筛查的顺序限制保留在本报告与 JSON 中，没有将其追溯改写成平衡实验。

本机与集群最终脚本哈希一致，独立补丁反向检查及 `git diff --check` 通过。求解器未修改，本轮使用针对原型的数值探针、逐次惯性检查和完整求解独立验收，没有重复运行未改变求解器的整套单元测试。

## 复现

源码、探针编译命令、固定排序筛查的 spec、所有 guard 记录、A/B 启动包装器和逐次报告均在归档中。完整对照示例（先停止同核范围内的其他构建和验收）：

```bash
cd /tmp/os2026-p10-repair.9doyhO
env/run.sh python tools/run/guard.py --exclusive --cores 8-15,16-23 --mem-gb 32 --timeout 1200 -- \
  python results/p12_compare.py \
  --binary hsolve-off=/tmp/os2026-p17/mpi-off \
  --binary hsolve-on=/tmp/os2026-p17/mpi-after \
  --solvers hsolve-off,hsolve-on --reps 3 --cores 8-15,16-23 --mem-gb 32 \
  --root /share/home/linzihan/p7_p7-membudget/data \
  --tag p17-pack-control-repeat --out-dir /tmp/os2026-p17 yee-pec-box-1e6
```

`mpi-off` 与 `mpi-after` 最终加载相同的 `pack.so` 和 P15 MPI 二进制，前者设置 `HS_PACK_ENABLE=0` 转发到原 OpenBLAS 打包。启用版的可复现源码是 `pack-single.cpp`；`pack-prefetch.cpp` 是另一实验，不能替换为它。归档包括固定排序文件；输入矩阵仍取上述数据目录。
